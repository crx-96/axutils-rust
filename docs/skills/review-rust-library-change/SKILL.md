# 审查 Rust library 变更

## 目的

为 Rust library 变更执行可重复、与工具无关的工作流。把仓库自身的规则、审查/验收标准、源码、manifest、测试和已发布文档作为主要上下文；不要凭空引入这些来源未支持的项目约定。

## 入口流程

1. 定位并读取适用的仓库规则、项目审查/验收标准、模块或架构定位文档；涉及开发或发布时再读取开发/发布指南。
2. 读取 manifest 的 package 元数据、features、dependencies 和 dev-dependencies。修改用户可见行为前确认当前版本和最低支持 Rust 版本。
3. 读取目标源码、公共重导出、附近调用方、现有测试、编译 fixture、API 文档、使用示例、README 相关段落和当前变更记录条目。
4. 记录需求行为、非目标、受影响文件、兼容性约束、外部副作用和验收所需证据。
5. 如果项目来源互相矛盾，先用源码和可复现编译/测试确定当前行为，再修改文档或实现。

## 影响分析

对每个适用维度分类；验证范围覆盖所有维度：

- 局部私有逻辑；
- 可观察行为、返回值、错误、默认值或限制；
- 公共模块、重导出、签名、trait、枚举、常量、别名、静态项或宏；
- feature 守卫、可选依赖、依赖 feature、MSRV 或包元数据；
- API 文档、使用示例、README、架构图/模块定位文档或变更记录；
- 安全、资源限制、并发、全局状态、`unsafe`、文件、网络、进程或 native toolchain 行为；
- 打包、发布或版本元数据。

在设计替代方案前追踪公共路径和调用链，搜索职责重叠的已有工具或领域类型。优先最小兼容变更，把无关重构排除在补丁外。

## 设计和实现

### 模块和 API 边界

- 把能力放到负责该职责的模块；职责、导出、依赖或范围变化时更新架构/模块定位文档。
- 除非明确要求删除，否则保留已有公共路径。记录所有支持的 crate 根路径、领域模块路径、兼容重导出和公开子模块路径；不要把私有文件写成导入路径。
- feature 守卫尽量精确。对模块、类型、方法、导入、测试、fixture 和示例使用实际所需的最窄组合。
- 后端可共享签名时，优先一个公共入口加显式后端选择；只有输入类型无法统一才使用带后缀方法；除非项目已接受这种兼容规则，不要创建“只在恰好启用一个后端时存在”的别名。

### feature 和依赖

- 第三方依赖设为 optional，并按仓库约定使用显式依赖 feature 绑定。
- 保持默认 feature 最小化和可选能力独立。除非是公共 API 所需且已记录的基础设施，不要让一个 feature 静默启用另一个项目能力。
- 同时检查正向和负向组合：预期导出应编译，缺少前置条件应失败，依赖树不能引入禁止后端或 runtime feature。
- 记录公共签名中的直接第三方类型、其 feature 要求和调用方责任。

### 实现质量

- 遵循仓库的 formatter、edition、命名、语言和错误约定。
- 用 `Result` 或 `Option` 显式表达失败；不对不可信输入静默吞错或使用无依据的强制转换、`unwrap`、`expect`、`panic!`。
- 评估复杂度、分配、拷贝、递归、输入大小、批量、重试、超时、并发、取消以及锁/连接池生命周期；对可能产生无界工作的不可信输入增加有界默认值和显式错误。
- 明确全局初始化、异步 runtime 所有权、惰性行为和外部副作用。除非项目明确规定，library 不应创建 runtime 或在纯构造函数中执行网络操作。
- 把 `unsafe` 作为单独的安全边界审查：记录不变量、平台前提、最小安全范围和专门测试。
- 不把 secrets、keys、原始配置、认证数据和敏感响应写入日志、错误字符串、fixture、示例或审查输出。

## 同步文档和测试

每个公共项或公共行为变化都同步适用内容：

1. API 文档：行为、参数、返回值、错误、限制、feature、外部副作用和聚焦的 `# Examples` doctest；
2. 详细使用文档：每个公共函数/方法独立小节及正常/边界示例；
3. 公共导入路径、枚举变体、trait 方法、常量、别名、静态项、宏和重要 trait 实现；
4. 架构/模块定位文档、README 概览，以及用户可见变化对应的变更记录；
5. 单元、集成、公共路径、边界、错误、并发和 feature/API 矩阵测试。

Markdown 含 Rust 代码时，在实际 feature 组合下编译所有受影响代码块。仓库不自动收集 Markdown 时使用临时文档测试 harness。网络、SMTP、Redis、写文件、进程或平台状态示例使用 `no_run` 或只构造对象；只用保留域名和占位凭据。

## 按影响范围选择验证

使用仓库提供的精确命令；没有时选择最接近、可复现的 Cargo 检查并报告范围：

| 影响 | 最小证据 |
| --- | --- |
| 仅私有局部逻辑 | formatter、直接测试、边界/错误测试、干净 diff 空白 |
| 公共行为/错误 | 上述证据，加上公共路径测试、API 文档/doctest、使用文档和回归覆盖 |
| 公共 API、feature、依赖或模块 | 相关正/负编译 fixture、依赖树、受影响 feature 测试和项目慢速矩阵 |
| 跨模块、安全、MSRV、Cargo 配置或发布 | 完整项目验证、文档 harness、package 文件清单，以及对跳过检查项的明确审查 |

只有在用户明确授权且仓库要求的环境和本地 ignored 配置都存在时，才运行 ignored live-service 测试。缺少真实服务不能用伪造成功替代。对于预期负向编译，核对诊断目标，不仅检查非零退出。

## 验收前复审

按以下顺序复审最终 diff：

1. 确认需求行为和非目标已满足，无无关修改。
2. 重新检查模块位置、公共路径、feature 守卫、依赖边界和兼容性。
3. 把所有用户可见行为变化与 API 文档、使用文档、README、模块定位文档和变更记录规则逐项对照。
4. 检查正常、边界、错误、负向 feature、公共导入和副作用测试。
5. 检查 secrets、错误输出、资源限制、异步/runtime 所有权、全局状态、`unsafe`、外部 I/O 以及 native/TLS 后端。
6. 每个声称的结果都对应命令输出或可复现产物；列出跳过、环境阻塞、预期失败、未解决风险和下一动作。

未具备证据的适用门槛不得标记完成。合理例外必须写明原因、替代证据、剩余风险、负责人或后续动作，以及是否需要用户确认。
